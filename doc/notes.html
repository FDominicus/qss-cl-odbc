Driver notes

Peculiarities of ODBC drivers found while testing qss-cl-odbc (2026). The test suite records them as features per database, so the tests that depend on them are skipped with the reason. Documentation

Microsoft Access (ACE ODBC driver, Windows)

  • Reserved words as column names (MEMO, DEC, TEXT …) give “Syntax error in field definition” in CREATE TABLE. Put every name in brackets: [text].
  • BINARY(n) has a fixed length: shorter values come back padded with zero bytes. Use LONGBINARY for binary data of varying length.
  • Types as reported: text as SQL_VARCHAR (not WVARCHAR; qss-cl-odbc reads it as UTF-16 anyway), CURRENCY as SQL_NUMERIC (read as an exact rational), Yes/No as 0/1 (not −1), SUM() over an INTEGER column as a double.
  • Decimal parameters: the driver rejects SQL_DECIMAL (HYC00, optional feature not implemented); qss-cl-odbc binds :decimal as SQL_NUMERIC.
  • Two connections: what one connection commits may reach another one only after about 5 seconds (the engine's page cache, PageTimeout). A changed row took 5 s; a new row was once visible at once and once not right after the commit. Do not rely on it.
  • No SQLForeignKeys: the driver does not support it (IM001 from the driver manager); get-foreign-keys signals an sql-error.
  • Object permissions from the .mdb era: a database once secured with a workgroup file (.mdw) and converted to .accdb keeps its owner. Over ODBC (user admin) reading and writing rows works, but CREATE TABLE fails with −1907 “no permission”. Importing the tables into a new .accdb removes the old owner.
  • Strict about buffer lengths: SQLGetInfo with buffer length 0 for a numeric value fails without a diagnostic record (older versions of plain-odbc did that; connecting failed).

PostgreSQL (psqlODBC)

  • Windows: switch off “LF <-> CR/LF conversion” (data source settings, Datasource → Page 2, or LFConversion=0 in the connection string). It is on by default and turns every LF into CR LF when reading: text changes silently.
  • Creating the test database: CREATE DATABASE x OWNER odbc_user ENCODING 'UTF8' TEMPLATE template0; since PostgreSQL 15 other users may not create tables in schema public.
  • Syntax errors in a transaction: psqlODBC before version 18 discards the whole transaction on a syntax error (psqlodbc issue #203), on other errors only the statement.
  • :string parameters: under Linux the Unicode driver rejects non-ASCII characters through SQL_C_CHAR (“Could not convert … to wide chars”); under Windows it accepts them. Plain strings (Unicode) always work.
  • No NUL character in TEXT; identifiers are cut to 63 characters without an error.
  • Output parameters work with functions through {call f(?, ?)}. Procedures (CREATE PROCEDURE) cannot be called this way (42809 “… is a procedure”).
  • Several statements in one call return several result sets; an error in a later statement is reported at execution.
  • Long diagnostic messages are split: psqlODBC cuts a message into several diagnostic records of the size of the first request (by design, see ER_ReturnError in environ.c), returning SQL_SUCCESS and the length of the part. The cut is counted in UTF-8 bytes: when it falls into a multi-byte character (any umlaut), SQLGetDiagRecW returns "Error: SqlState=…" instead of the text, and the message is lost (psqlODBC 16). qss-cl-odbc asks with an 8190-character buffer first and reads again when the buffer was full.

SQLite (Christian Werner's sqliteodbc)

  • ANSI text is UTF-8, also under Windows: connect with :ansi-encoding :utf-8 (connect-sqlite does) when using :string or :clob parameters. With Windows-1252 the bytes are stored raw and characters are lost when reading.
  • BLOBs reported as BINARY(255): with bound columns longer values are cut (with a warning). Set (use-bind-column con) to NIL to read them completely.
  • Values as stored: text is cut at a NUL character; doubles keep 15 digits (0.30000000000000004 comes back as 0.3); VARCHAR(n) lengths are not enforced; there are no exact decimals: NUMERIC(10,2) is stored as REAL and comes back as a double.
  • Integer expressions reported as 32 bit: every integer expression without a declared type (sum(…), literals, even CAST(… AS BIGINT)) is described as SQL_INTEGER, and read as SQL_C_SLONG the driver cuts it to 32 bit without an error (3000000000 → -1294967296; found with Chinook: sum(Bytes) 117386255350 → 1422138358). SQLite always computes with 64 bit, so qss-cl-odbc reads SQL_INTEGER columns of SQLite connections as 64 bit (integer-as-bigint).
  • SQL: no ODBC escapes such as {fn UCASE(…)}; one statement per call.
  • Locking: with autocommit off (qss-cl-odbc's default) a connection that only read still holds its transaction and blocks writers (“database is locked”). Use *connect-autocommit* for readers, or commit/rollback after reading.
  • Linux build is an ANSI driver: unixODBC converts SQL text beyond Latin-1 with losses (a column alias Ωx became ©x). Values passed as parameters are not affected.

MySQL / MariaDB (MariaDB Connector/ODBC)

Tested on Linux with MariaDB 10.11 and MariaDB Connector/ODBC 3.1.15 (Unicode driver). MySQL's own Connector/ODBC is not tested yet.

  • Characters U+xxD8 to U+xxDB (for example Ø, U+00D8): drivers before 3.1.24 and 3.2.10 take the low byte of each UTF-16 unit for the start of a surrogate pair (MariaDB issue ODBC-502, fixed in August 2026). Writing appends NUL characters ("aØb" is stored as "aØb\0"); reading reports too few bytes ("aØb" comes back as "aØ"). Reproduced in plain C, so not a qss-cl-odbc problem: update the driver. The test suite detects the bug by behaviour and skips the affected checks.
  • Text is cut at a NUL character when read, although the server stores it.
  • Row counts: UPDATE returns the number of changed rows, not the matched ones, unless the connection uses the option for found rows (FOUND_ROWS=1 / OPTION=2).
  • 16 MB column sizes: TEXT types and catalog columns are reported with sizes such as 16777216. qss-cl-odbc reads character and binary columns larger than *max-precision* with SQLGetData (before 2026-10-14 this was an error “column … larger than maximum size”).
  • DDL commits implicitly; TIMESTAMP starts in 1970 (use DATETIME); TEXT holds 64 KB (use LONGTEXT).

Driver managers

  • unixODBC: only the development package provides libodbc.so; qss-cl-odbc loads libodbc.so.2, which the runtime package has.
  • Headers differ in a few constants that qss-cl-odbc does not use: SQL_API_SQLCANCELHANDLE is 1550 in Microsoft's headers and mingw-w64, 1022 in unixODBC (2.3.12 and current source); SQL_SPEC_* is 4.00 in microsoft/ODBC-Specification, 3.80 in mingw-w64, 3.52 in unixODBC (qss-cl-odbc leaves them out). (qss-cl-odbc-generate:check) lists the differences for a platform.
  • SQL_C_BOOKMARK depends on the pointer size (64 bit: −27, 32 bit: −18).

Notes

This documents contains some observations and pitfalls encountered when using different drivers and databases. Of course this list is not complete. Also some of these problems might have vanished in the mean time.

driver-connect

Using driver-connect one does not have to create an ODBC datasource for every database one wants to use. The necessary parameters for the driver manager/driver are supplied via connection string. Some connection strings examples for using driver-connect
  • using the excel driver "DRIVER={Microsoft Excel Driver (*.xls)}; DBQ=C:/TEMP/Book1.xls"
  • using the access driver: "Driver={Microsoft Access Driver (*.mdb)};DBQ=c:/temp/Copy of OMR TT Reports.mdb"
  • using an Oracle Driver "DRIVER=Oracle in oracl92;UID=SCOTT;PWD=tiger;server=ltrav1"
One way to get a connection string is to create a file dsn and have a look at its contants, note that userid and password are encrypted in this file,

Problems using the Jet driver on windows

It seems that the jet driver needs to have write access to the registry directory HKEY_LOCAL_MACHINE\SOFTWARE\ODBC, see PRB: Error Message: 0x80004005: General Error Unable to Open Registry Key . In the mentioned document these steps are recommended
  • 1. Start Registry Editor (Regedt32.exe).
  • 2. Select the following key in the registry: HKEY_LOCAL_MACHINE\SOFTWARE\ODBC
  • 3. On the Security menu, click Permissions.
  • 4. Type the required permissions for the account that is accessing the Web page.
  • 5. Quit Registry Editor

driver-connect, another approach

Oracle and ref cursors

This works with 9.2 and 10g and 10gR2. Make sure that the ODBC datasource is configured correctly. On the "Oracle ODBC Driver Configuration" window check the checkbox with label "Enable Result Sets".
Example: 
create or replace package test99_pkg as        
  type refcursor is ref cursor;       
  procedure test_cursor(v varchar2,c in out refcursor);      
end;

create or replace package body test99_pkg as       
  procedure test_cursor(v varchar2,c in out refcursor) is
  begin         
    open c for select v as a,'1234567890' as b from dual; 
  end;      
end;
The cursor can be retrieved with following lisp code: 
(with-prepared-statement (stm con 
                                "{call test99_pkg.test_cursor(?,?)}" 
                                '(:string :in ))
    (let ((str "just a string"))
      (exec-prepared-query stm str)))
Note that the cursor parameter must be declared in/out. If a parameter ist supplied for the cursor parameter, it still works. This needs more investigations.

Parameters

As mentioned in the documentation, MySQL does not support out and in/out parameters for sql statements. As the documentation of MySQL suggest one should declare variables, pass them as parameters to the stored procedures. After the procedure call one get there contents with a select statement, example: select @param1 as param1,@param2 as param2.

The problem with variables on MySQL is that one can only set them. It is not possible to declare a datatype for them. Another option is to select the parameters directly in the stored procedure. Thus instead of having out or in/out parameters, the procedure returns return values as a result set. Note that exec-query accepts parameters and can return more than one result set. One example, assume *con* is a MySQL connection. 

[33]>  (exec-command *con* "
    create procedure test99(a1 varchar(200),b1 int,c1 date) 
    begin
    declare a2 varchar(200);
    declare b2 int;
    declare c2 date;
     set a2=concat(a1,'x');
      set b2=b1+3;
      set c2=c1+ interval 1 day;
      select a2 as a2,b2 as b2, c2 as c2;
    end;")
